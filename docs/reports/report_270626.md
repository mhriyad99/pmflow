# PMFlow — Professional Process Manager Roadmap

**Current Version:** 1.2.16  
**Date:** 2026-06-27  
**Author:** Md. Mahmudul Hasan Riyad

---

## Executive Summary

PMFlow is a lightweight CLI process manager that wraps subprocesses with persistent JSON state, group relationships, and pause/kill lifecycle controls. The fundamentals are solid: clean module separation, a Singleton state manager, Typer-based CLI, and psutil for cross-platform process ops.

This report identifies the gaps between the current implementation and a professional-grade tool, then lays out a prioritized plan to close them.

---

## Current Strengths

- Clean command separation: `create`, `kill`, `ls`, `pause`, `respawn`, `recreate`
- Group/parent-child model for multi-service management
- Rich table output plus JSON export for scripting
- Works on Linux, macOS, and Windows
- Published to PyPI (`pip install pmflow`)

---

## Critical Gaps

### 1. State File Location

**Problem:** `processes_state.json` lives inside the installed package directory (`pm/processes_state.json`). This means:
- State is wiped on every `pip install --upgrade`
- Multiple users on the same machine share no isolation
- The file ends up inside `site-packages`, which is not writable on many systems

**Fix:** Move state to a user-local config directory using Python's `platformdirs` library.

```python
from platformdirs import user_data_dir
STATE_FILE = Path(user_data_dir("pmflow", "mhriyad99")) / "processes_state.json"
```

This resolves to `~/.local/share/pmflow/` on Linux, `~/Library/Application Support/pmflow/` on macOS, and `%APPDATA%\pmflow\` on Windows — all upgrade-safe and user-isolated.

---

### 2. No Automated Tests

**Problem:** There are zero tests. Every change risks silent regressions.

**Fix:** Add a `tests/` directory with pytest. Priority test targets:

| Test area | What to cover |
|-----------|---------------|
| StateManager | add, remove, update, get, persistence round-trip |
| `pm create` | happy path, duplicate name, missing group errors |
| `pm kill` | by PID, by group, --all flag, cascade to children |
| `pm ls` | table output, JSON output, --running filter |
| `pm pause` / `pm respawn` | SIGSTOP/SIGCONT round-trip |

Use `typer.testing.CliRunner` for CLI integration tests and `unittest.mock.patch` to mock `subprocess.Popen` and `psutil`.

Add CI via GitHub Actions (`.github/workflows/test.yml`) running the suite on Python 3.10, 3.11, and 3.12 on Ubuntu, macOS, and Windows.

---

### 3. Log Management

**Problem:** There is no stdout/stderr capture for spawned processes. If a process fails silently, there is no way to diagnose it without attaching a debugger.

**Fix:** Add a `--log-file` option to `pm create` and a `pm logs <name|pid>` command.

```
pm create "uvicorn app:app" --name api --log-file ~/.local/share/pmflow/logs/api.log
pm logs api          # tail -f equivalent
pm logs api --lines 50
```

Store the log file path in `processes_state.json` alongside existing metadata. Use `subprocess.Popen` with `stdout` and `stderr` redirected to the log file on creation. For the `pm logs` command, stream the file with a polling loop (or `watchdog` for inotify-based tailing).

---

### 4. Daemon / Background Process Reliability

**Problem:** Processes created with `pm create` are children of the `pm` process. When the terminal closes, SIGHUP is sent and background processes may die unless the user manually calls `nohup` or `disown`. The `--foreground` flag exists but background mode reliability is not guaranteed.

**Fix:** Use double-fork (Unix) or a `CREATE_NEW_PROCESS_GROUP` + `DETACHED_PROCESS` flag combination (Windows) to fully detach spawned processes from the calling terminal.

```python
# Unix
import os
if os.fork() != 0:
    os._exit(0)
os.setsid()
if os.fork() != 0:
    os._exit(0)
```

On Windows, pass `creationflags=subprocess.DETACHED_PROCESS | subprocess.CREATE_NEW_PROCESS_GROUP` to `Popen`.

### 5. Process Status Accuracy

**Problem:** `pm ls` updates statuses at query time, but there are only three states: `running`, `paused`, `doesn't exist`. If a process crashed with a non-zero exit code, it shows as `doesn't exist` — indistinguishable from a process that was never created.

**Fix:** Expand the status enum in `schema.py` and track exit codes.

```python
class Status(str, Enum):
    RUNNING = "running"
    PAUSED = "paused"
    STOPPED = "stopped"       # exited cleanly (code 0)
    CRASHED = "crashed"       # exited with non-zero code
    UNKNOWN = "unknown"       # pid reused by OS or state stale
```

Store `exit_code` and `exited_at` in the JSON when psutil reports the process is gone. Use `psutil.Process.status()` to distinguish `psutil.STATUS_STOPPED` from a dead process.

---

### 6. No `pm start` / `pm stop` as Aliases

**Problem:** The mental model for users coming from PM2, systemd, or Supervisor is `start`/`stop`/`restart`. PMFlow uses `create`/`kill`/`recreate`, which are accurate but unfamiliar.

**Fix:** Add aliased commands that map to existing logic.

```
pm start  → alias for pm create
pm stop   → alias for pm kill (graceful SIGTERM before SIGKILL)
pm restart → pm kill + pm recreate for a specific process
pm status  → alias for pm ls
```

Typer supports this cleanly with command aliases or thin wrapper functions.

---

### 7. Configuration File Support

**Problem:** Every `pm create` invocation requires all flags inline. There is no way to codify a set of services (like a `docker-compose.yml` or `Procfile`) and bring them all up with a single command.

**Fix:** Add support for a `pmflow.yaml` project-level config file.

```yaml
# pmflow.yaml
version: 1
processes:
  api:
    command: uvicorn app:app --host 0.0.0.0 --port 8000
    group: backend
    relation: parent
    log_file: logs/api.log
  worker:
    command: celery -A tasks worker
    group: backend
    relation: child
```

Add two commands:

```
pm up              # reads pmflow.yaml in CWD, starts all processes
pm down            # stops all processes defined in pmflow.yaml
```

Use `PyYAML` or `tomllib` (Python 3.11+ stdlib) for parsing.

---

### 8. Signal Handling Gaps

**Problem:** `pm kill` sends SIGKILL immediately (on Unix, via `psutil.kill()`). This does not allow graceful shutdown — database connections stay open, in-flight requests are dropped, etc.

**Fix:** Implement graceful stop with a timeout.

```
pm stop <name>              # SIGTERM, wait 10s, then SIGKILL
pm stop <name> --timeout 30 # SIGTERM, wait 30s
pm stop <name> --force      # immediate SIGKILL (current behavior)
```

Use `psutil.Process.terminate()` then `psutil.wait_procs([proc], timeout=N)` to implement this cleanly.

---

### 9. No `pm info` / Process Detail View

**Problem:** `pm ls` shows a summary table. There is no way to inspect a single process in detail (start time, memory usage, CPU, command with full arguments, log path).

**Fix:** Add `pm info <name|pid>`.

```
pm info api

  Name:        api
  PID:         12345
  Status:      running
  Command:     uvicorn app:app --host 0.0.0.0 --port 8000
  Group:       backend
  Relation:    parent
  Started:     2026-06-27 09:14:32
  Uptime:      4h 22m
  CPU:         1.2%
  Memory:      128 MB (RSS)
  Log file:    ~/.local/share/pmflow/logs/api.log
```

`psutil.Process` already exposes `cpu_percent()`, `memory_info()`, `create_time()`, and `cmdline()`.

---

### 10. Stale State Cleanup

**Problem:** If the machine reboots, all PIDs in `processes_state.json` are stale. On the next `pm ls`, every process shows as `doesn't exist`, but the entries are not cleaned up automatically. `pm recreate` will restart all of them, but there is no checkpoint to know which ones *should* auto-restart vs. which were intentionally stopped.

**Fix:** Add an `autostart` flag to process metadata (default `true`) and a `pm cleanup` command.

```
pm cleanup           # removes all entries whose pid no longer exists
pm recreate --auto   # recreates only processes with autostart: true
```

On first `pm ls` after reboot (detected by checking if `uptime < process.create_time`), print a warning: "X processes have stale PIDs. Run `pm recreate` to restart or `pm cleanup` to clear."

## Architecture Improvements

### Extract a `ProcessRecord` Dataclass

`schema.py` currently has only a bare `Relation` enum. All process metadata is stored as plain `dict`. Replace this with a typed dataclass:

```python
from dataclasses import dataclass, field
from datetime import datetime
from typing import Optional

@dataclass
class ProcessRecord:
    pid: int
    command: str
    name: Optional[str]
    group: str
    relation: str          # Relation enum
    status: str            # Status enum
    exit_code: Optional[int] = None
    log_file: Optional[str] = None
    autostart: bool = True
    created_at: str = field(default_factory=lambda: datetime.utcnow().isoformat())
    exited_at: Optional[str] = None
```

This makes the state schema explicit, self-documenting, and easy to validate. Use `dataclasses.asdict()` for JSON serialization.

### Add `settings.py` Properly

The current `settings.py` is 4 lines long and hardcodes the state file path inside the package. Expand it to a proper settings module:

```python
from platformdirs import user_data_dir, user_log_dir
from pathlib import Path

DATA_DIR = Path(user_data_dir("pmflow"))
LOG_DIR = Path(user_log_dir("pmflow"))
STATE_FILE = DATA_DIR / "processes_state.json"
CONFIG_FILE = Path.cwd() / "pmflow.yaml"

DATA_DIR.mkdir(parents=True, exist_ok=True)
LOG_DIR.mkdir(parents=True, exist_ok=True)
```

### Add a `version` Command

```
pm version
pmflow 1.2.16
```

Use `importlib.metadata.version("pmflow")` so it always reads from the installed package metadata — no hardcoding.

## Prioritized Implementation Plan

1. Move `processes_state.json` to `platformdirs` user data dir
2. Add `ProcessRecord` dataclass and migrate state schema
3. Expand `Status` enum with `stopped`, `crashed`, `unknown`

## Summary

PMFlow has a clear identity and a working foundation. The four changes that will have the most immediate professional impact are:

1. **Move the state file** out of the package directory (prevents upgrade data loss)
2. **Add log capture** (makes the tool actually useful for production services)
3. **Add graceful stop** (prevents data corruption in managed processes)
4. **Add automated tests** (makes future changes safe to ship)

Everything else builds on those four. With Phase 1 complete, PMFlow is a tool you can recommend to a team. With all four phases done, it is a credible lightweight alternative to PM2 for Python-centric stacks.
